Cases

Ten times my coding agent repeated a fix it already knew. Two of them still got through.

These come from 9 months of my own Claude Code and Codex history. Each one is an error that an earlier session had already worked out, often in another repo, and that came back anyway.

I replayed every case with only the history from before that moment, and checked what nanaoki would have shown the agent. Most of the time it had the fix. Sometimes it didn't, so the misses are here too.

The message in each terminal is what nanaoki 0.1.1 prints today for the same error. I changed project names, paths and hosts. The error and the shape of the fix are real.

The verdicts come from my replay, scored by a Claude judge, on my own data. "AGENTS.md alone" is a file written from the same history and loaded on every turn.

01Shell#zsh-glob

zsh gives up on a glob that matches nothing

$ ls -a ../web/.dev.vars* (eval):1: no matches found: ../web/.dev.vars*
Before
Fixed in project-a, about 8 months earlier
This time
project-b
AGENTS.md alone
Prevented

This is my most common repeat: 465 sessions across 54 projects. Bash passes an unmatched glob through, but zsh stops the whole command. The agent adds quotes and moves on, then the next session does the same thing.

Caught by a guard before running The glob matched no file, so the guard warned and gave the quoted command.
02Shell#zsh-equals

A row of equals signs breaks a zsh command

$ ax "…/listing/1234" --md; echo =====; ax "…/listing/5678" --md (eval):1: ===== not found
Before
Hit and fixed in project-c, about 2.5 weeks earlier
This time
a scratch folder
AGENTS.md alone
Not prevented

The agent wanted a separator between two outputs. In zsh, a word that starts with = expands to the path of a command, so ===== goes looking for a program called ====. My AGENTS.md had notes on zsh quoting, but nothing about =.

Blocked by a guard before running The command can't work as written, so this guard blocks it instead of warning.
03Node/JS#node-version

The build wants Node 22. The shell has another one.

Before
Fixed in the same project, 7 hours earlier
This time
project-d
AGENTS.md alone
Not prevented

The repo pins Node 22, and a newer Node was first on PATH. One session found the fix. Seven hours later, a new session started from zero. The only Node advice in my AGENTS.md was "use bun", which does nothing for a version pin.

Caught by a guard before running The guard compares the pin with the node on PATH. If the build runs anyway, the lesson comes after the failure.

08Preferences#dont-change-yet

"Don't make any changes yet"

> how could this be fixed? just asking, don't make any changes yet
Before
I typed some version of it in 181 sessions
This time
project-m
AGENTS.md alone
Prevented

This repeat is mine, not the agent's. I ask a question and the agent starts editing files. nanaoki shows the rule at the first prompt of a session when the words match. The AGENTS.md file got it too. A rule this stable belongs in the file, and nanaoki rules suggest proposes the line for you.

09Shell#wrong-lesson

A missing file, read as a missing tool

$ rg -n "deploy" apps/cms/CLAUDE.md apps/web/CLAUDE.md rg: apps/cms/CLAUDE.md: No such file or directory (os error 2)
Before
Same error in the same project, about 4 months earlier
This time
project-g
AGENTS.md alone
Not prevented

The agent guessed a path that didn't exist. nanaoki matched the error to the wrong cause and said the tool was missing. The tool was fine, and the file just wasn't there. A lesson that points the wrong way costs more than no lesson at all.

Missed The lesson matched the words of the error, not its cause.
10Preferences#code-comments

Comments that only restate the code

No error. The agent writes the code comments I keep asking it not to write.
Before
Asked for in earlier sessions. The AGENTS.md written from them has the line.
This time
project-o
AGENTS.md alone
Prevented (the second judge said no)

My rule is to comment only when the code can't explain itself. Nothing fails when the agent ignores it, so no hook fires after an error. The first prompt of the session didn't share enough words with the rule either. This is what the always-loaded file is good at.

Missed A style rule has no error for a hook to match.
